# Where does a new colour go?

Use this decision framework when you need to add a colour to the codebase. It ensures colours end up in the right layer.

### Is it decorative: a tag, a project, a chart series?

→ Add to `tokens.json` as its own group, alongside `chart`, not under `color`.
→ Does NOT need a primitive scale.
→ These are identifiers that need to be distinct from each other, not UI roles.

Tag and project colours are still hardcoded in `constants.ts`. That is debt, not
the pattern: colour belongs to the colour system, and `constants.ts` should hold
none of it. Do not add to it.

### Does it fit an existing colour family?

→ Use the closest primitive from `tokens.json`.
→ Pick the nearest step in the 50–950 scale.
→ Create or use a semantic token in `tokens.json` for the UI role.
→ Available families: **slate, purple, red, green, gold, blue, orange**.

### Is it a completely new hue not covered by any family?

→ This is rare. Discuss with the team first.
→ If approved: add a full 50–950 scale to the `primitives` block in `tokens.json`.
→ Then create semantic tokens that reference it.
→ Example: product adds a pink/magenta brand element.

## What is NOT a semantic token

- **Tag colours** — values a user picks when creating a tag. They do not map to a primitive family, and forcing them into scales would cost the visual distinction they exist for.
- **Project colours** — assigned by index for project avatar badges.
- **Chart/data viz palettes** — the `chart` group in `tokens.json`. Themed, but scoped to one feature rather than a cross-cutting UI role.

Tags and projects are decorative rather than semantic, but they are still colour,
so they belong in `tokens.json` beside `chart`. Both are in `constants.ts` today,
along with `colours.primary` and `colours.white`, which simply restate
`--primary-500` and `--always-white`.
- **Third-party brand colours** — GitHub, Google, etc. Use their official values directly.

## How to create a semantic token

### 1. Name it

Follow the naming convention: `--color-[category]-[variant]`

<table>
  <thead>
    <tr><th>Part</th><th>Options</th><th>Example</th></tr>
  </thead>
  <tbody>
    <tr><td><code>category</code></td><td><code>surface</code>, <code>text</code>, <code>border</code>, <code>icon</code></td><td><code>--color-text-</code></td></tr>
    <tr><td><code>variant</code></td><td><code>default</code>, <code>secondary</code>, <code>disabled</code>, <code>danger</code>, <code>success</code>, <code>warning</code>, <code>info</code>. Surface also has: <code>subtle</code>, <code>muted</code>, <code>emphasis</code>, <code>hover</code>, <code>active</code>. Text also has: <code>tertiary</code>.</td><td><code>--color-text-danger</code></td></tr>
  </tbody>
</table>

### 2. Pick the primitive values

Open `tokens.json` and choose the right step from the 50–950 scale in `primitives`. The pattern for light vs dark:

<table>
  <thead>
    <tr><th>Variant</th><th>Light mode</th><th>Dark mode</th><th>Why</th></tr>
  </thead>
  <tbody>
    <tr><td><code>default</code></td><td>500–600</td><td>400–500</td><td>Needs to read well on light/dark surfaces</td></tr>
    <tr><td><code>hover</code></td><td>600–700 (darker)</td><td>400–600 (lighter)</td><td>Light: darken on hover. Dark: lighten on hover.</td></tr>
    <tr><td><code>active</code></td><td>700–800 (darkest)</td><td>300–400 (lightest)</td><td>More intense than hover in both modes</td></tr>
    <tr><td><code>subtle</code></td><td>8% opacity of default</td><td>Opaque dark tint</td><td>Light: transparent tint. Dark: opaque to avoid stacking issues.</td></tr>
  </tbody>
</table>

### 3. Add to `tokens.json`

Add the token entry to the appropriate colour category with `light` and `dark` values:

```json
{
  "color": {
    "text": {
      "danger": {
        "cssVar": "--color-text-danger",
        "light": "#ef4d56",
        "dark": "#ef4d56"
      }
    }
  }
}
```

Run `git commit` — the pre-commit hook generates `_tokens.scss` and `tokens.ts` automatically.

### 4. Use it

```scss
// In SCSS — each element type gets its own token
.banner--danger {
  background: var(--color-surface-danger);
  color: var(--color-text-danger);
  border: 1px solid var(--color-border-danger);
}
```

```tsx
// Icons reference the icon token
<Icon fill="var(--color-icon-danger)" />

// Or via TS exports — flat camelCase constants
import { colorIconDanger } from 'common/theme/tokens'
<Icon fill={colorIconDanger} />
```

Dark mode works automatically — no extra overrides needed.

### 5. Verify

- Run Storybook and check the **Design System / Semantic Tokens** story — your new token should appear automatically.
- Toggle light/dark in the toolbar and confirm both values look correct.
- Check contrast: text tokens on surface tokens should meet WCAG AA (4.5:1 for normal text, 3:1 for large text).

### Common mistakes

- **Using a hex value instead of the JSON** — always add tokens to `tokens.json`, never edit `_tokens.scss` or `tokens.ts` directly.
- **Forgetting the `dark` value** — every colour token needs both `light` and `dark` in the JSON. Missing it means the light mode value shows in dark mode.
- **Using transparency in dark mode subtle tokens** — use opaque values in dark mode to avoid stacking/blending issues with layered surfaces.
- **Using one token for multiple element types** — don't use `--color-text-danger` for a background. Text, surface, border, and icon each have their own danger token with values optimised for that context.
