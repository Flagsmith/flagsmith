Once an experiment is running, Flagsmith serves the variations automatically through the flag. Your application has two
jobs:

1. **Record exposures**: tell Flagsmith when an identity actually experienced a variation.
2. **Record conversion events**: send the events your metrics aggregate.

## Wiring checklist

Experiment results are only valid if every item below holds. Most of these mistakes don't throw an error; they silently
corrupt the results. The calls for each SDK are in the tabs below.

1. **One stable identifier per visitor, and check that it really is stable.** Exposures and conversions are joined per
   identifier. For anonymous visitors, generate a random ID once, store it in a cookie, and reuse it on every later
   request. Never create a new ID per request, and never hard-code an ID such as `user_42` from the examples below. Web
   frameworks often do not parse cookies for you, and a missing parser silently creates a new ID on every request. So
   before you finish, verify it: request the page twice, sending back the cookie from the first response, and confirm
   the same identifier is used both times.
2. **Record the exposure where the variation is shown.** Get the experiment flag for that identifier in the request that
   renders the variation. See [Record exposures](#record-exposures).
3. **Record the conversion when the action happens, with the same identifier.** Track the event in the handler for the
   action, using the identifier from the visitor's cookie. See [Track conversions](#track-conversions).
4. **Create the client once, at startup, with events enabled.** Don't create a client per request. When self-hosting,
   set the events URL with the exact option shown in your SDK's tab under [Initialise](#initialise).
5. **Send buffered events before the process exits.** Events are sent in batches every 10 seconds. Close or flush the
   client on shutdown (for example in your `SIGTERM` handler), or events still in the buffer are dropped.
6. **Keep serving the page when Flagsmith is unreachable.** Give the client a short request timeout and a default flag
   handler that returns the control value, and catch errors from flag calls, so an outage falls back to the control
   value instead of failing or hanging the request.

## Instrument your application

Users must be [identified](/flagsmith-concepts/identities). Exposures and conversion events are joined per identity, so
use the same identifier for flags and events.

### Initialise

Enable events when you create the client, with the environment key you already use for flags. Events accept the
client-side key and server-side keys.

When self-hosting, also point the SDK at your Flagsmith API and your event ingestion service, as in the commented lines
below. Otherwise the SDK sends events to Flagsmith Cloud. If you use the Flagsmith database, set the events URL to your
Flagsmith API URL ending in `/api/` instead. See [Self-Hosting and Open Source](/experimentation/self-hosting).

The SDKs buffer events and send them in batches, by default every 10 seconds. Send what is left before your application
exits, as shown in each tab.

<Tabs groupId="language" queryString>
<TabItem value="js" label="JavaScript">

```javascript
import flagsmith from '@flagsmith/flagsmith';

await flagsmith.init({
    environmentID: 'YOUR_CLIENT_SIDE_ENVIRONMENT_KEY',
    enableEvents: true,
    // Self-hosted only:
    // api: 'https://flagsmith.example.com/api/v1/',
    // eventProcessorConfig: { eventsApiUrl: 'https://events.flagsmith.example.com/' },
});
await flagsmith.identify('user_42');

// Before a server-side render responds, or before the page unloads
await flagsmith.flushEvents();
```

`eventProcessorConfig` requires `enableEvents: true`; `init` throws without it.

</TabItem>

<TabItem value="python" label="Python">


`flagsmith.models`, not from `flagsmith`.

to `EventProcessorConfig` so each event is sent as it is tracked.

### Record exposures

An exposure is the moment an identity is served a variation; it is what enrols them in the results. Getting the
experiment flag evaluates it and records the exposure in one call.

<Tabs groupId="language" queryString>
<TabItem value="js" label="JavaScript">

```javascript
import flagsmith from '@flagsmith/flagsmith'; // the client from Initialise

const flag = flagsmith.getExperimentFlag('checkout_button');
// ...render based on flag.value
```

</TabItem>
<TabItem value="react" label="React">

```jsx
import { useExperiment, useFlagsmith } from '@flagsmith/flagsmith/react';

function CheckoutButton() {
    const flagsmith = useFlagsmith();
    const flag = useExperiment('checkout_button'); // null until flags load

    return (
        <button onClick={() => flagsmith.trackEvent('purchase', { value: 99.5 })}>
            {flag?.value === 'buy_now' ? 'Buy now' : 'Checkout'}
        </button>
    );
}
```

The experiment flag call records the exposure as soon as it evaluates the flag, so use it where the user actually
experiences the change. If you evaluate in one place and display in another, don't use it. Evaluate with the SDK's
normal flag call instead, which records nothing, then record the exposure yourself at the point of display. Only record
it for identities enrolled in the experiment:

<Tabs groupId="language" queryString>
<TabItem value="js" label="JavaScript">

```javascript
import flagsmith from '@flagsmith/flagsmith'; // the client from Initialise

// Evaluate without recording an exposure
const flag = flagsmith.getAllFlags().checkout_button;

// ...later, at the point of display
if (flag?.experiment?.inExperiment) {
    flagsmith.trackExposureEvent('checkout_button', { value: flag.variant });
}
```

</TabItem>
<TabItem value="react" label="React">

`useExperiment` records the exposure when the component renders. To record it elsewhere, read the flag with `useFlags`
and call `trackExposureEvent` from `useFlagsmith()`, as in the JavaScript tab.

</TabItem>


Exposures are deduplicated per identity: each identity is counted once, in the variation it saw first, so recording an
exposure more than once is safe.

The event name is **case-sensitive** and must exactly match the metric's configured event name. Unmatched events are
silently ignored. Conversions are attributed post-exposure: an identity's events only count after its first exposure.

### Troubleshooting

The SDKs skip events silently rather than throw. If the **Exposures** panel stays empty, check that:

- The environment has a [connected warehouse](/experimentation/connect-a-warehouse). The event ingestion service rejects
  events for environments without one.
- The user is identified. Exposures without an identity are skipped.
- Every variation of the flag has a label. Exposures are attributed by label, so a variation without one, for example
  one created through the API without a `key`, is not counted.
- The identity is inside the experiment's rollout. Identities outside it are not enrolled and record no exposure.
- Buffered events were sent before your application exited. See [Initialise](#initialise).
- Event names match your metrics exactly, including case.
- Event timestamps are within the accepted window. Events older than 10 days or more than 24 hours in the future are
  rejected, and a batch over 2 MiB is rejected whole.

To see why an event was skipped, turn on your SDK's debug logging.

## While it runs

- The flag is locked while the experiment is running.
- Monitor enrolment on the experiment page's **Exposures** panel to confirm data is arriving.
- You can edit the rollout from the experiment page, but changing it mid-experiment can affect the statistical validity
  of your results.
